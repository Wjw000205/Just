# 研发与生产大数据平台需求基线

> 状态：开发工作基线（文档冲突项按“更严格要求优先”处理；标记为 `TBD` 的事项不得据此对外承诺）。
>
> 来源：①《研发与生产大数据平台数据库建设软件开发需求文档-0408》；②《研发与生产大数据平台项目实施方案修改2》。

## 1. 基线结论与术语

- 项目目标是建设企业内部统一的“材料—工艺—半成品/成品—性能—产品”研发与生产数据平台，覆盖采集、治理、检索、追溯、审核、共享、导出、归档和审计，为后续 AI 工艺优化、质量预测及数字孪生提供数据基础。
- 用户所述 `pq + MongoDB` 应按 `PG/PostgreSQL + MongoDB` 理解。两份源文档均明确指定 PostgreSQL，全文没有将 `pq` 定义为独立数据库或组件。除非用户后续明确否定，工程统一使用 `PostgreSQL` / `PG` 命名；`libpq` 仅是 PostgreSQL 客户端库，不是本项目的数据存储选型。
- PostgreSQL 存储强一致、可关联、可审计的结构化业务数据；MongoDB GridFS 存储 3D 模型、CT/金相图像、仿真文件、报告等非结构化大文件。灵活数据集记录放 PostgreSQL JSONB 还是 MongoDB 必须按数据性质确定，不能简单地把所有记录都放进动态 MongoDB 集合。
- Redis 是实施方案正文中的实际依赖，承担验证码、登录失败/账号锁定、令牌撤销、分布式锁、热点搜索与短期缓存；它虽未列入总架构表，但用户已明确要求，纳入正式技术基线。
- 本期默认采用 Spring Boot 3.x、Vue 3、PostgreSQL、MongoDB、Redis、Docker；MES/PLM/ERP 和工业设备在缺少真实接口、SDK、样例文件及网络条件时，只能完成适配框架、模拟器和契约测试，不能宣称完成生产联调。

## 2. 范围与优先级

### P0：可运行核心平台

1. 登录认证、用户、部门、多角色 RBAC、数据域、菜单/API/按钮权限和审计。
2. 模板/模板片段创建、编辑、版本、发布申请、审核、停用、收藏。
3. 数据集创建、动态表单、在线录入、批量导入、附件上传、查询、导出和操作留痕。
4. PostgreSQL + MongoDB GridFS + Redis 的完整读写链路。
5. 材料/批次/工艺/产品/性能/检测的正向和反向追溯最小闭环。
6. 首页指标、检索、数据集、追溯、设备、审计和系统管理基础页面。
7. Docker 化本地部署、数据库迁移、种子数据、健康检查、API 文档与自动测试。

### P1：合同功能闭环

1. 数据审核、电子签名/二级确认、发布、选择性共享、全生命周期归档。
2. 分类树、数据标签、数据字典、导出任务、批量文件导入及失败明细。
3. 设备时序数据、告警、附件在线预览、追溯链可视化、管理看板和报表。
4. 不可篡改审计、数据变更历史、跨库备份恢复和恢复演练。

### P2：依赖外部条件的生产集成

1. MES、PLM、ERP 的真实字段映射、增量游标、Webhook、回写、对账和补偿。
2. 3D 打印、氧化、三坐标、硬度、金相/厚度、疲劳设备的厂商协议适配。
3. 生产消息队列、API 网关、限流熔断、死信重试、IP 白名单和外部应用鉴权。
4. 历史数据盘点、清洗、迁移、验证及正式验收环境的性能/安全/兼容性测试。

## 3. 角色基线

源需求称“四类核心用户”但实际列出五类，实施方案又使用另一组系统角色。基线将“业务角色”和“系统授权角色”统一为可配置的多角色 RBAC；用户可绑定多个角色，并叠加一个或多个数据域，权限取并集、数据范围受最小范围约束。

| 角色 | 核心职责 | 基础权限 |
|---|---|---|
| 研发人员 `RND` | 材料、工艺、仿真、研发试验数据 | 录入、查询、修改本人/本域数据、导入导出、追溯 |
| 生产操作人员 `PRODUCTION` | 设备、生产批次、工序执行 | 设备监控、采集、录入、查询、追溯 |
| 质量控制人员 `QUALITY` | 检测、缺陷、质量审核和异常批次 | 录入、审核、导出、正反向质量追溯 |
| 系统管理员/运维 `ADMIN` | 用户、角色、数据域、配置、备份、监控 | 全局管理；高风险操作仍须二次确认和审计 |
| 企业决策层 `EXECUTIVE` | 看板、报表、趋势和汇总 | 脱敏只读、授权导出，不得直接修改业务数据 |
| 审核员 `AUDITOR` | 模板、数据、发布审批 | 审核/驳回/停用/发布；应与提交人职责分离 |
| 数据管理员 `DATA_ADMIN` | 模板、数据集、标准与数据质量 | 数据治理、分类、字典、迁移、发布协调 |
| 访客 `GUEST` | 公开数据浏览 | 仅公开、只读、默认无下载 |

## 5. 核心业务流程

1. **身份与授权**：管理员建用户/审批注册 → 分配多角色与数据域 → 用户登录 → 服务端认证 → 每次请求执行 API 权限和数据域过滤 → 记录审计。
2. **模板发布**：创建私有或公共模板 → 配置章节、字段、单位和校验 → 保存版本 → 公共模板提交 → 独立审核员通过/驳回 → 发布或退回 → 全程留痕。
3. **数据采集发布**：选择模板建数据集 → 在线填写或批量导入/设备接入 → 格式、必填、单位、业务规则校验 → 暂存 → 提交审核 → 通过后发布/共享；驳回保留原因和原版本。
4. **全链路追溯**：登记材料批次 → 关联工艺批次和参数 → 关联零件/产品批次 → 关联性能与质检 → 从任一节点双向展开关系、原始记录、附件和审计事件。
5. **检索与导出**：用户提交组合条件 → 自动叠加数据域过滤 → 返回分页/高亮结果 → 校验导出权限和二级确认 → 流式生成文件 → 记录字段、条数、大小和操作者。
6. **外部系统接入**：接收/拉取数据 → 鉴权和幂等校验 → 字段映射/清洗/单位转换 → 异步缓冲 → 分流写入 PG/Mongo → 对账；失败进入重试/死信并告警。
7. **生命周期**：依据策略从在线转归档 → 保持索引和可追溯性 → 定期备份 PG、Mongo 与文件 → 校验备份 → 执行恢复演练并生成报告。

- `Approval`、`ElectronicSignature`、`AuditEvent`、`DataChange`、`ExportJob`、`RetentionPolicy`、`ArchiveRecord`、`BackupRecord`。

### 6.2 研发、生产与追溯

- `Material`、`MaterialBatch`、`Supplier`、`Composition`。
- `ProcessDefinition`、`ProcessBatch/Run`、`ProcessParameter`、`ProductionOrder`、`OperationStep`。
- `Part/Product`、`ProductBatch`、`Model/Simulation`。
- `PerformanceTest`、`Inspection`、`Measurement`、`Defect`、`Report`。

- `ExternalSystem`、`IntegrationConfig`、`FieldMapping`、`SyncCursor`、`IntegrationJob`、`DeadLetter`、`ReconciliationResult`。

所有受控业务记录至少包含：唯一标识、业务编码、数据域、来源系统/来源记录号、版本、状态、创建/修改人和时间、逻辑删除标志；需要 ALCOA+ 的数据修改不得覆盖原值。

## 7. 权限与安全基线

- 后端权限判断是安全边界；前端隐藏菜单/按钮仅改善体验，不能代替鉴权。
- 支持多角色。数据域至少支持全局、部门、研发项目、产品线，并允许一名用户绑定多个数据域。
- 操作权限至少覆盖录入、查询、修改、删除、导入、导出、审核、发布、共享、停用和管理。
- 查询、导出、文件预览/下载、追溯图的每个节点均须执行数据域过滤，防止通过 ID 猜测或关联关系越权。
- 密码只在服务端使用 BCrypt/Argon2id 等抗暴力破解算法存储；HTTPS 已提供传输保护。实施方案的“前端 SHA-256 后再 BCrypt”存在口径与安全设计歧义，未确认前不作为验收要求。
- 生产环境不应把长期令牌放在 `localStorage`；建议短期访问令牌内存保存，刷新令牌使用 `HttpOnly + Secure + SameSite` Cookie，或采用经安全评审的等效方案。
- 敏感配置通过环境变量/密钥管理注入，不写入代码或镜像；外部接口采用独立身份、最小权限、HMAC/OAuth2、IP 白名单和重放保护。
- 审计日志追加写入、禁止更新/删除，并通过摘要链或等效机制检测篡改。需求文档要求“永久保存”，因此在双方确认其他期限前，不能用实施方案的“不少于 10 年”降低要求。
- 电子签名必须绑定具体记录版本、签名人、时间、含义/原因和认证证据；普通“二级密码确认”不能自动等同于完成 FDA 21 CFR Part 11 合规验证。

## 9. 验收口径

1. 合同范围内功能全部交付，功能用例通过率 ≥98%，无阻塞/严重缺陷，一般缺陷 ≤5 且不影响使用。
2. 性能按第 8 节指标测试；报告必须记录硬件、数据量、脚本、并发模型、预热方式、采样时长和分位数。
3. 安全测试覆盖认证、授权、数据域、文件、导出、接口签名、注入、XSS/CSRF、依赖漏洞和敏感信息泄漏；无高危漏洞，中危修复率 ≥90%。
4. 追溯验收至少用一个真实或等比例样例，验证“材料批次→工艺批次→产品→检测”及“缺陷→产品→工艺→材料”的双向路径和附件/审计证据。
5. 导入迁移需输出总数、成功数、失败数、重复数、校验摘要及差异清单；抽样和全量规则由双方签字确认。
6. 备份恢复必须实际演练 PostgreSQL、MongoDB/GridFS 和配置恢复，达到确认后的 RPO/RTO。
7. 合规验收需要需求—控制—测试—证据矩阵，不能仅以功能演示代替。
8. 正式上线后试运行 3 个月；稳定且满足业务需求后完成最终验收。

## 10. 两份文档的冲突、歧义与缺口

| 编号 | 级别 | 问题 | 工作基线/待确认事项 |
|---|---|---|---|
| C-01 | 高 | `pq` 未定义，但两文档均写 PostgreSQL | 按 PG/PostgreSQL 实施；若用户原意不是 PG，需立即变更 |
| C-02 | 高 | 需求称“四类”却列五类；实施方案的系统角色又不一致 | 采用第 3 节角色集，角色可配置 |
| C-03 | 高 | 需求一处写“每用户唯一角色”，另一处写“用户多角色绑定”；实施表结构只给单 `role_id` | 以多角色为准，使用 `user_role` 关联表 |
| C-04 | 高 | 需求要求结构化数据进 PostgreSQL；实施方案又把动态数据集记录全部放 MongoDB | 强一致核心数据进 PG；非结构化文件进 GridFS；灵活记录按数据性质评审 |
| C-05 | 高 | 要求材料—工艺—产品—性能全链路，实施数据库表只详述用户/模板/数据集/日志 | 必须补充领域实体/统一追溯实体及关系，不能以模板数据集代替追溯模型 |
| C-06 | 高 | 审计日志“永久保存”与“不少于 10 年”冲突 | 未确认前按永久保存；归档但不可删除/篡改 |
| C-07 | 高 | ALCOA+/Part 11 被写成原则，缺少记录版本、电子签名绑定、职责分离和验证证据 | 纳入 P1 合规控制；由质量/法规负责人确认 |
| C-08 | 高 | MES/PLM/ERP 无真实接口定义；文档存在空缺映射句和空查询示例 | 生产集成为 P2；先做适配框架、模拟契约和字段映射表 |
| C-09 | 高 | 设备协议大量缺失，三坐标型号“待确认” | 获取厂商 SDK/手册、样例报文/文件和联调环境后才能承诺接入 |
| C-10 | 中 | 高并发方案写“Kafka 或 RabbitMQ”，技术选型未定且用户只明确 Redis | 生产前必须选型；MVP 可用可替换接口/Redis Streams，不得假定已满足大规模削峰 |
| C-11 | 高 | 实施方案写 PostgreSQL TDE、MongoDB 加密存储引擎，可能受版本/发行版/授权限制 | 生产前确认版本与许可证；可采用磁盘/卷加密和字段加密的可验证替代方案 |
| C-12 | 中 | 登录协议混用前端 SHA-256 与后端 BCrypt，且示例/处理流程不完全一致 | 采用 TLS + 服务端 BCrypt/Argon2id；若需双重哈希，另写兼容协议 |
| C-13 | 中 | JWT 存 local/sessionStorage 与高安全目标存在 XSS 风险 | 采用内存访问令牌 + HttpOnly 刷新令牌或经评审的等效方案 |
| C-14 | 高 | 时序化存储是需求，但实施方案无明确模型、分区、保留与降采样策略 | 用 PG 分区/BRIN 或评审扩展；建立保留、归档和查询策略 |

## 11. 技术栈映射

| 需求能力 | 技术实现 |
|---|---|
| Web 前端/动态表单/看板 | Vue 3 + TypeScript + Vite + Element Plus；路由和按钮按权限元数据控制 |

## 12. 开发期间的需求变更规则

1. 本基线 ID 是需求、代码、测试和验收的统一引用；后续变更必须记录提出人、原因、影响、优先级和批准结论。
2. `TBD` 项可以提供模拟实现或安全默认值，但不能包装成已完成的生产能力。
3. 两份文档冲突时依次采用：双方签字变更/合同 → 明确的需求文档条款 → 实施方案；安全、数据完整性和验收指标取更严格值，直到书面确认放宽。
4. 开发完成的最小定义：代码、数据库迁移、API/页面、自动测试、权限/审计验证、部署说明和追踪矩阵状态同时完成。
